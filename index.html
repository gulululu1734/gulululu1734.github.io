QQ 流量分析（PC–PC 端、PC–手机端）

分析对象：pc-pc.pcapng（542 包 / 19.93 s）、pc-mobile.pcapng（1640 包 / 19.51 s）、data.bin　｜　工具：Wireshark 4.6.9

核心结论：QQ 的文件本体走 TCP。PC–PC 是点对点直连且被 TLS 1.3 加密，无法还原；PC–手机 是”在线中转”，用明文 HTTP(8080) 上传到 QQ 文件服务器，可还原。本次已成功恢复 1 个 PNG 文件。

一、总体结论（作业答案核心）

对比项 pc-pc.pcapng（PC–PC 端） pc-mobile.pcapng（PC–手机端）
文件传输协议 TCP（UDP 只跑心跳/在线状态） TCP（UDP 只跑心跳/信令）
传输方式 点对点直连（P2P）：本机 50468 → 对端 IPv6:443 在线中转：POST 到 QQ 文件服务器 157.148.55.114:8080
加密 / 明文 加密：TLS 1.3，应用数据全为密文 明文：HTTP 请求头 + 原始文件字节可见
能否恢复文件 不能（无密钥） 能，已还原 1 张 PNG 图片
恢复结果 — 9193EE214DDCCC5B2FB405CAEC7B229B.png，486×652，427,237 B，MD5 9193ee214ddccc5b2fb405caec7b229b

二、判断过程与证据

1. 用什么协议：TCP 还是 UDP

统计 → 会话（Conversations），按字节数排序：

  • pc-pc.pcapng：最大的流是 TCP [2409:895c:…:ca88]:50468 ↔ [2408:8748:c110:333::31]:443，190 包 / 约 197 kB，其中下载 192 kB、持续 0.55 s，就是这次传文件的流（tcp.stream eq 34）。
  • pc-pc.pcapng：UDP 只有 172.20.10.10:19420 ↔ 112.49.67.69:11091 等 9 个包、约 1.3 kB，载荷是 QQ 私有混淆格式、仅几十字节，不含文件内容。
  • pc-mobile.pcapng：最大的流是 TCP 172.20.10.10:59078 → 157.148.55.114:8080，497 包 / 458 kB，其中上传 447 kB（tcp.stream eq 67）。
  • pc-mobile.pcapng：UDP 只有 11091（心跳）与 6896 / 6996 等端口的小包，同样是信令。

结论：文件数据本身走 TCP；QQ 的 UDP 只用于保活、在线状态和打洞探测。

2. 加密还是明文

（1）pc-pc.pcapng —— 加密（TLS 1.3）

  • 过滤 tls.handshake 可见 Client Hello（frame 306）与 Server Hello（frame 311）。
  • Client Hello 的 SNI 直接是对端的 IPv6 地址 2408:8748:c110:333:31::（不是域名），说明是点对点直连。
  • supported_versions = 0x0304（TLS 1.3），服务器选定 TLS_AES_128_GCM_SHA256（0x1301）。
  • 之后该流全是 Application Data，看不到请求行、文件名或文件头。

用文件头特征码搜索，全部落空：

  • 整份 pc-pc.pcapng 里唯一可读的 HTTP 是微信的 /mmtls/… 与 Windows 联网探测，与本次 QQ 传文件无关。

（2）pc-mobile.pcapng —— 明文（QQ 私有 httpconn + HTTP）

过滤 http.request 直接就能读出：

  • 0x6ff0082 = PicUp.Echo：客户端先向候选服务器（157.148.55.114:8080、122.96.96.144:443）发探测，收到 200 OK 后再选一条上传。
  • 0x6FF0087 = PicUp.DataUp：真正携带文件。请求在 frame 1101 开始、body 一直到 frame 1515，服务器在 frame 1598 回 200 OK（152 B，回包里带 PicUp.DataUp 与同一个 MD5）。
  • 在”追踪流 → TCP”里可直接看到 89 50 4E 47 0D 0A 1A 0A（PNG 文件头），文件内容完全可读 → 明文。

3. 恢复明文文件

上传请求体（Content-Length: 428597）中，QQ 的封装格式为：

偏移 长度 内容
0x00 1 0x28（’(‘）帧开始标记
0x01 4 00 00 05 46 = 1350，其后的 protobuf 元数据长度
0x05 4 00 06 84 E5 = 427 237，文件长度
0x09 1350 protobuf 元数据（PicUp.DataUp、uin、文件名、MD5、下载 URL…）
0x549 427 237 文件原始字节（从 89 50 4E 47 开始）
末尾 1 0x29（’)’）帧结束标记

元数据中可直接读出的关键字段：

恢复步骤（特征码定位法）：

  • 定位 tcp.stream eq 67（或过滤 http.request.method==”POST” && http.request.uri contains “6FF0087”）。
  • 在字节视图搜 PNG 文件头 89 50 4E 47 0D 0A 1A 0A，命中位置 frame 1102（文件内偏移 1359）。
  • 从该处取到结束块 00 00 00 00 49 45 4E 44 AE 42 60 82（IEND+CRC），另存为 .png；也可用”追踪流 → TCP → Raw”另存后按偏移切分。
  • 校验：427 237 字节；IHDR 中宽 0x01E6 = 486、高 0x028C = 652、位深 8、颜色类型 6（RGBA）；MD5 = 9193ee214ddccc5b2fb405caec7b229b，与报文中的 MD5、文件名完全一致 → 恢复完整、成功。

三、为什么 PC–PC 端恢复不出来

  • 该流是 TLS 1.3：密钥由 ECDHE 临时协商，抓包中只有 Client Hello / Server Hello / Application Data，没有密钥材料，也没有可用 RSA 私钥解出的预主密钥。
  • 而且它是直连（SNI 就是对端 IP，没有经过 QQ 的明文中转服务器），所以也没有”服务器上存在明文文件”这条退路。
  • 因此 PC–PC 流量只能做流量层面分析（五元组、连接时长、上下行字节数、包长分布、时序特征），不能还原文件内容。
  • 想解密只有两个前提：抓到 SSLKEYLOGFILE（客户端密钥日志）或拿到服务器私钥，本实验都不具备。

四、关于导出的 data.bin（这里有个坑）

data.bin 不是文件本体，原因有两条：

  • 取错流了：它来自 tcp.stream eq 9（[2408:8756:f50:3049::20]:443 ↔ 本机:64434），是一条 TLS 加密流，本就不含明文文件；真正传文件的是 tcp.stream eq 67（157.148.55.114:8080）。
  • 保存格式错了：它是”追踪 TCP 流 → 显示为 ASCII”后另存的文本——不可打印字节全部被替换成 ‘.’（0x2E），方向切换处插入 0x09(Tab)，所以满屏 2E 2E 2E 2E 24 73 …。
  • 校验：tcp.stream 9 的有效载荷共 5016 字节，data.bin 为 5028 字节（多出的是换行/Tab 等文本字节），前缀与 ASCII 视图逐字节一致，可确认来源。
  • 因此拿它去搜 FF D8 FF（JPEG 头）当然”找不到”。正确做法是在 tcp.stream eq 67 上”追踪流 → Raw”（或”文件 → 导出对象 → HTTP”），再按 89 50 4E 47 定位切分。

五、结论（简版）

  • UDP or TCP？文件传输走 TCP（PC–PC 用 443 直连；PC–手机 用 8080 的 HTTP 上传）。QQ 同时使用 UDP（11091、6896/6996 等）发送心跳、在线状态与打洞探测，但这些小包不携带文件数据。
  • 加密 or 明文？PC–PC：加密，TLS 1.3（0x0304，TLS_AES_128_GCM_SHA256），SNI 为对端 IP，属点对点直连，应用数据不可读。PC–手机：明文，QQ 私有 httpconn 协议跑在 HTTP/1.1 上（htcmd=0x6FF0087，uin=2787197981），请求头、文件名、MD5、文件内容全部可见。
  • 恢复明文文件：用文件头特征码定位——PNG 89 50 4E 47 0D 0A 1A 0A、JPEG FF D8 FF、PDF 25 50 44 46、ZIP 50 4B 03 04、RAR 52 61 72 21、GIF 47 49 46 38；从特征码截取到文件结束标志（PNG 为 IEND+CRC）即可还原。本次从 pc-mobile.pcapng 的 tcp.stream 67 还原出 9193EE214DDCCC5B2FB405CAEC7B229B.png（486×652，427 237 B，MD5 9193ee214ddccc5b2fb405caec7b229b，与报文 MD5 一致）。链路：PC 172.20.10.10:59078 → QQ 文件服务器 157.148.55.114:8080（/cgi-bin/httpconn?htcmd=0x6FF0087），手机端再从 multimedia.nt.qq.com.cn/download?appid=1406&fileid=… 下载，即”在线传输（服务器中转）”。
  • 两种方式的差别：在线中转（PC–手机）为兼容与穿透走 HTTP 明文，可被直接还原；点对点直连（PC–PC）已用 TLS 1.3 加密，抓包也无法还原。所以”QQ 文件传输能否被还原”不能一概而论，要看走的是哪条路径。

六、复现步骤（Wireshark 操作清单）

1. 打开 pc-mobile.pcapng → 统计 → 会话 → TCP，按 Bytes 排序，找到 172.20.10.10:59078 ↔ 157.148.55.114:8080（447 kB）。

2. 右键该会话 → 追踪流 → TCP，”显示数据为”选 ASCII，可看到 POST /cgi-bin/httpconn?htcmd=0x6FF0087&uin=2787197981，往下就是 ‰PNG。

3. 过滤 http.request.method==”POST” → 文件 → 导出对象 → HTTP；或按 tcp contains 89:50:4e:47 定位后”显示分组字节 → 另存为”。

4. 用 HxD 打开导出文件：确认开头 89 50 4E 47 0D 0A 1A 0A、结尾 49 45 4E 44 AE 42 60 82；计算 MD5 与报文中的 9193ee214ddccc5b2fb405caec7b229b 对比。

5. 打开 pc-pc.pcapng → 过滤 tls → 选中 tcp.stream eq 34 的 Client Hello，查看 SNI=2408:8748:c110:333:31::、supported_versions=0x0304，确认 TLS 1.3 加密；再用 tcp contains 搜各类文件头，验证无明文文件。
